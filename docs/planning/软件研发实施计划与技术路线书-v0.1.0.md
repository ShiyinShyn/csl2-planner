## 1.【系统需求与数据流分析】

### 1.1 产品目标、系统边界与需求分层

系统在地形和水域约束下，生成可编辑、可比较、可追溯的城市规划方案。每个业务模块都必须具有完整的“输入 → 候选方案 → 约束校核 → 用户调整 → 重算 → 输出 → 验收”链路；共享数据底座、交通需求模型和几何引擎，不把任何一个业务模块降格为仅展示图层。

**建议的首个完整版本范围**：五大模块全部覆盖，先实现规划级算法、可编辑方案和基础校核；强化求解精度、动态仿真规模与高级三维表现分级迭代。首版不能以“仅支持用地与路网”代替五模块完整交付。

| 需求编号 | 完整业务单元及必须覆盖的能力 | 核心成果 | 验收责任 |
|---|---|---|---|
| FR-LU | 用地规划：陆地识别；城市用地/自然保护区区分；地形分区；功能自动分配；用户修改 | 陆水分区、保护/开发约束、地形分区、规划用地、分配依据与变更记录 | GIS 算法工程师 + 产品负责人 |
| FR-RN | 路网规划：完整四阶段法；道路外部连接候选与选址；公路/主干路/次干路/支路分级；每个交通小区独立街区尺度 | TAZ、分目的/分时段 OD、分方式需求、分级道路、流量及可达性、TAZ 参数 | 交通算法工程师 |
| FR-ID | 内部道路规划：地块出入口；内部微观交通组织；配建停车与公共停车 | 出入口、车行/步行与转向关系、内部通路、停车供需与设施布局、局部运行评估 | 交通算法工程师 + GIS 工程师 |
| FR-PT | 公共交通规划：海运/铁路外部连接走廊；地铁线网；客运火车站及轨道走廊；港口及航道；公交客运站/枢纽 | 外部走廊、地铁候选网、铁路车站/轨道、港口/航道、公交客运站/枢纽、换乘和服务评估 | 交通算法工程师 |
| FR-HW | 公路入城规划：过境公路/城市道路连接点；周边 TIA；立交及匝道几何 | 接点方案、无建设/建设/改善场景、影响报告、立交拓扑、平纵断面与匝道校核 | 交通算法工程师 + 产品负责人 |

**非功能要求建议**：离线本地可用、原始数据不可改写、工程可重复计算、异步任务可取消、用户编辑可撤销、方案版本可追踪、导入错误可解释、输出支持通用 GIS 交换。性能、平台和工程上限在 G0 基准测试后确认。

**不应混淆的边界**：

1. 地形适建性只能支持“保护候选/不宜开发区”判断，不能凭坡度自动证明真实生态或法定保护区属性；正式保护范围由用户明确指定或输入可信补充图层。
2. 四阶段法和局部仿真不是游戏内部交通 AI 的等价复制；无观测数据时，结果是基于假设的场景估算。
3. 立交和匝道必须提供规划级几何，而不是只画示意连线；但施工图级结构、岩土、水工和法定道路审查不默认纳入。
4. 已核查的 Carto 文档说明的是导出能力。本计划不假设 Carto 可以反向导入规划、创建道路或自动施工。[R1]
5. 机场、完整物流供应链、水动力/洪水模拟不擅自新增为必交范围；客货运边界须确认。

### 1.2 真实样例审计与适配结论

本地样例目录：`GIS-files-example/`。原始数据不随公开仓库分发；下述为已有本地样例的审计摘要。公开自检使用合成数据，数据与资料范围见 [DATA_SOURCES.md](../../DATA_SOURCES.md)。

本次使用 TIFF 元数据与像素读取、SHP/DBF 文件头和属性读取进行只读检查。结果已保存至 `docs/planning/carto-sample-data-audit.json`。**未进行全量几何有效性、路网连通性或游戏内对照验证。**

| 实际文件（统一前缀为 ZUTTOMAYO CITY） | 实测结构/规模 | 接口用途及风险 |
|---|---|---|
| `Elevation.tif` | 4096 × 4096，Float32，3.5 m/像素；有效高程约 22.9535–618.7126 m | 必选 DEM；高程基准须保留为游戏基准，不当成真实海拔 |
| `Depth.tif` | 2048 × 2048，Float32，7 m/像素；有效水深约 0.00004953–172.6516 m | 水域必选输入的一种合规载体；先排除 NoData，再提取水域 |
| `Area_Boundary.shp` | 536 面：529 个 MapTile、7 个 District | 地图范围、地块解锁状态与行政区；行政区不是天然 TAZ |
| `Building_Boundary.shp` | 3,127 面；含 Resident、Employee、Category、Zoning | 现状居民/就业与设施约束；不能直接等价为未来需求 |
| `Network_Centerline.shp` | 3,967 线；Road 2,204，Track 746，Pathway 684，Waterway 266，Taxiway 63，Runway 4 | 多模式网络；须分类后建图，不能将所有线当成道路 |
| `Network_Boundary.shp` | 3,963 面 | 路权/占地与现状障碍；与中心线记录数不同，不能按行号一对一关联 |
| `POI_Location.shp` | 845 点；含 Parking、StopBus、StopSubway、TrafficLight 等 Category | 现状设施与站点补充；点位不代表设施规模、容量或完整信号配时 |
| `Route_Centerline.shp` | 21 线：Bus 8、Train 5、Subway 4、Tram 4 | 现状线路参照；Passenger、Usage 等属性不能直接当作完整 OD 或连续流量 |
| `Zoning_Boundary.shp` | 33,333 面；含 Name、Color、Object、Zoning | 游戏分区单元；不能直接等价为本工具规划地块或 TAZ |

**关键事实及工程含义**：

- 样例 GeoTIFF GeoKey 为 EPSG:32631；Shapefile 的 `.prj` 同为 WGS 84 / UTM zone 31N，线性单位为米。保留其投影和实际仿射变换，不凭文件名推定其他数据同样如此。
- 两个栅格在标签中均声明 NoData 为 `1.70141e+038`。这是有限浮点数，因此单独使用 `isfinite`/`isnan` 判断无效值是不够的。Depth 有效像素数为 3,250,910；DEM 为 16,777,216。
- Carto 作者文档说明 Depth 中非正水深的陆地区域可写为 NoData；Elevation 相对于游戏原点，而非海平面。[R2] **只有确认数据覆盖完整、没有缺测后，Depth 的 NoData 才能按该语义归为非水域；一般 GIS 数据的 NoData 仍应视为未知。**
- 样例没有独立水域面。`Network` 中的 Waterway 是航道网络，不是水域边界。本工具须从 Depth 正有效像素生成水域，不能拿航道缓冲替代水体。
- DEM 和 Depth 具有不同像素大小，不能按数组行列直接叠加。先校验投影、仿射和覆盖范围，再执行显式重采样。
- 样例中心线是二维 PolyLine，桥隧信息位于 `Form` 等属性。`Elevation` 属性不能替代逐顶点高程；二维交叉不等于拓扑连通。
- 样例没有完整的稳定实体 ID、车道逐向结构、转向限制、信号配时、交通 OD 或时间序列。以上数据采用补充参数、推断及人工确认，必须标记来源。
- `.cpg` 声明 UTF-8；本次 DBF 字符字段严格 UTF-8 解码检查未发现非法字段值。不得因终端显示乱码而擅自转码原文件。
- `tifffile` 在枚举页目录时出现 `invalid page offset` 警告，但首波段成功读取。P0 必须用拟采用的 GDAL 驱动与 QGIS 复核读写兼容性；当前既不能据此宣称文件损坏，也不能宣称全部兼容。

### 1.3 必选、可选 GIS 与非 GIS 参数契约

Carto 官方支持 GeoTIFF 栅格及 Shapefile/GeoJSON 矢量，几何和字段可由用户配置，因此导入器采用“能力发现 + 版本化适配”，不要求全部可选字段永远存在。[R1][R2]

| 输入角色 | 是否必选 | 接受形式及语义 | 缺失时行为 |
|---|---|---|---|
| 地形 `terrain_elevation` | **必选** | Carto Elevation GeoTIFF，或经显式校验的等价 DEM；须有可解析的单位、栅格定位和无效值规则 | 拒绝启动规划计算，保留导入诊断 |
| 水域 `water_extent` | **必选** | 优先 Carto Depth GeoTIFF，经无效值处理得到水域；也可接受已明确 CRS、有效范围的水域面 | 拒绝启动规划；不允许只靠单一高程阈值猜测水域 |
| 航道水深 `water_depth` | 条件能力 | 输入为 Depth 时随必选水域一起获得；若仅有水域面则可能缺少 | 允许水域与陆地规划；港口/航道可做几何筛选，但水深可行性不可标为通过 |
| 项目/地图范围 | 可选 GIS、必需的派生配置 | 优先 Area 中 MapTile 合并；缺少时从有效 DEM 覆盖与用户 ROI 明确确定 | 展示采用的范围与裁切影响，不增加第三个强制 GIS 图层 |
| 现状用地、建筑、人口/就业、设施 | 可选 | Zoning、Building、POI、Area | 转入新城情景；以用户目标人口、就业、容积率等非 GIS 参数估算 |
| 现状道路、轨道、航道、公交线路 | 可选 | Network、Route | 新建候选网络；外部连接采用明确的情景网关，而非宣称识别出真实连接 |
| 自然资源、保护区、景观、土壤等 | 可选 | 用户提供的补充图层或绘制约束 | 仅输出保护候选与不确定性，不伪造生态属性 |
| 世界地形/水深 | 可选 | World Elevation/World Depth | 外部走廊研究限制在已知范围；不推断未知世界段可施工 |
| 规划参数 | **非 GIS 配置** | 目标人口/就业、开发强度、TAZ 街区尺度、峰时系数、方式偏好、设计速度、资产尺寸、船型/车辆参数等 | 提供版本化情景默认值，并要求关键假设显式确认 |

**两类运行模式**：

- **新城规划模式**：只有 DEM + 水域即可进入全部模块的方案生成；需求与设计参数来自已标记的情景假设。关键数据不足的专项校核返回“待补资料”，而不是静默通过。
- **既有城市改造模式**：使用可选现状数据校准与约束。能否称为“已校准”，取决于是否有独立观测，不取决于是否导入了建筑图层。

### 1.4 数据标准化、清洗与质量门禁

**推荐目录分层**：原始只读快照 `raw` → 规范化数据 `normalized` → 分析派生层 `derived` → 情景 `scenario` → 方案结果 `results` → 交换成果 `exports`。

1. **登记与快照**：记录城市名、游戏版本、Carto 版本或 unknown、导出设置、导出时间或 unknown、文件校验值、缺失附件。建议游戏暂停后成套导出；无法证明同一时刻的数据标记为快照一致性未知。
2. **输入解析**：GeoTIFF 读取 CRS、仿射、像素大小、波段类型、NoData；Shapefile 检查 `.shp/.shx/.dbf` 配套、`.prj/.cpg`；GeoJSON 单独解析坐标体系，不因同一目录而假定与栅格相同。
3. **坐标统一**：分析采用以米为单位的项目 CRS；保存原始 CRS、变换与游戏坐标映射。缺少 CRS 时停止自动对齐，允许用户明确映射，不“猜测成功”。
4. **栅格规范化**：先构造有效掩膜；连续 DEM 可采用适当连续插值；水域分类掩膜用最近邻，水深插值仅在已知水体内部执行，禁止跨岸线污染。保留原始 3.5/7 m 细节；粗分辨率只服务于候选搜索，不冒充提高精度。
5. **陆水识别**：标准水域为覆盖有效且水深为正的区域；近零水深建立可配置不确定带，不凭任意阈值消灭浅水。陆地为研究范围中已知非水域部分；未知覆盖区单列。
6. **几何与属性**：检测空几何、自交、多部件和重复记录；修复前后保存差异；分类字段按枚举/逗号分隔标签解析；未知类型入隔离区。`Addr_dist` 等字段通过显式映射进入规范名，保留原名。
7. **道路拓扑**：按 Object/Category 分模式；Direction 转为有向边；平面交叉结合端点、Form、层级、可用高程及人工确认建图。桥隧不可仅因投影交叉而连通。Lane、Limit、Elevation 的逐向/单位/基准含义列入适配验证。
8. **质量输出**：阻断项、可降级项、警告分别出报告。有效值范围、陆水面积守恒、投影误差、未解析类型、孤立组件及连接歧义可在地图定位。

### 1.5 规范数据模型、接口与追溯

| 实体 | 关键字段/约束 |
|---|---|
| DatasetManifest | 数据角色、源路径、校验值、版本、CRS、单位、覆盖、NoData、快照一致性 |
| Terrain/Water | 地形、水深、水域/未知掩膜、分辨率、质量标记 |
| Constraint | 类型、几何、硬/软、优先级、来源、可否由用户解除 |
| LandUseZone / Parcel / TAZ | 三者分离；功能、面积、开发量、人口/就业假设、TAZ 街区参数 |
| NetworkNode/Link/Turn | 模式、方向、层级、长度、容量假设、几何、结构层、转向、源要素关联 |
| DemandScenario / OD | 出行目的、时段、方式、人数/车次单位、外部/内部/过境类型、估计与观测区分 |
| Facility / Alignment | 出入口、停车、车站、枢纽、港口；平面线形、纵断面、资产包络和校核状态 |
| PlanVariant / Evaluation | 父方案、参数版本、人工锁定、模型版本、随机种子、任务结果、违反约束及不确定性 |

**关联原则**：导入时生成项目内主键并保留源记录号；跨快照匹配使用几何/属性匹配与冲突确认，不把源记录号或坐标哈希误称为游戏稳定实体 ID。

**拟定计算协议**：任务输入包含 `project_id / scenario_id / input_revision / module / parameters / random_seed`；任务返回 `job_id / status / progress / diagnostics / artifacts`。方案、单位和模型版本全程随成果传递；过期输入结果不覆盖当前方案。

**数据来源标签**：观测 `observed`、用户输入 `user`、推断 `inferred`、默认假设 `assumed`。工程版本和来源可证明追溯，但不能替代精度验证。

### 1.6 数据流与跨模块迭代

```text
Carto 导出 + 可选补充图层 + 显式规划参数
    → 数据适配/质量门禁 → 米制项目坐标与规范数据底座
    → 地形派生/陆水与硬约束
    → M1 用地方案 ↔ TAZ 与需求生成
    → M2 四阶段法/外部网关/分级路网
         ├→ M3 地块出入口/内部组织/停车
         ├→ M4 海运铁路外部走廊/地铁/站港枢纽
         └→ M5 公路入城接点/TIA/立交匝道
    → 共享评估与约束复核 → 用户编辑/锁定 → 增量重算
    → GIS 成果 + 方案比较 + 假设与可行性报告
```

**必须显式实现的反馈**：公交服务改变方式划分，重新影响道路需求；停车与出入口改变局部需求/转向；立交接点改变外部交通分配；路网用地与交通可达性反向影响 M1。采用有界外层迭代、松弛与明确停止规则；超时/不收敛保留候选和残差，不无限循环。

用户修改某 TAZ 街区参数只使相关局部细分及必要的需求/网络依赖失效；不得无说明覆盖其他 TAZ 或人工锁定成果。

## 2.【分阶段研发里程碑】

### 2.1 周期、人员与估算前提

**建议基线：28 周研发 + 4 周风险储备，总窗口 32 周。** 该估算以“6 人等效团队、规划级完整五模块、本地单用户、无自动施工、使用既有开源 GIS/求解/仿真组件”为前提；不是已批准的工期承诺。

建议人员：技术负责人/产品 1、GIS 算法 1、交通算法 1、后端与工程化 1、前端 GIS 1、测试与数据质量 1。需要交通规划领域评审参与关键闸口。28 周对应约 168 人周基线投入；储备最多另增 24 人周。人周不等于报价，也不代表可无限并行。

**周序按立项启动计算，不预设实际开工日期**。多用户、完整三维编辑、自动建造、施工图或高保真全城仿真一旦批准，重新估算人员与关键路径，不塞进原工期。

### 2.2 阶段分解与交付

#### B. 交通校准与验证

- **模型校验**：无观测时，用守恒、解析网络、极端案例和参数敏感性检查模型实现；结果标记“情景估算/未校准”。
- **校准**：取得游戏观测流量、旅行时间、队列等后，校准与观测目的相关的参数；若需新增采集模组，须单独确认。
- **独立验证**：使用未参与调参的另一时段/存档/快照，检查误差及变化方向；不把调参数据再次拟合称为独立验证。[R5]
- **微观仿真试验**：预热期剔除、多个随机种子、报告均值/分位数/置信区间；建议最少 10 次，再根据统计稳定性增加，次数与终止条件在 G0 设上限。仿真值不等于游戏实测值。[R4]
- **无足够观测的发布策略**：不阻止提供规划辅助功能，但必须持续显示假设、敏感区间与“未经游戏观测校准”，且不使用“准确预测游戏交通”的宣传表述。

#### C. 非功能与发布

建议基准机为 Windows、8 核 CPU、16 GB 内存、SSD；实际规格由用户确认。以本次样例为基线，建议导入/规范化 ≤2 分钟、峰值内存 ≤6 GB、交互响应 p95 ≤300 ms（不包含异步算法耗时）、一次宏观计算 ≤10 分钟、单个局部 TIA 的预定义试验批次 ≤20 分钟。**这些是待基准验证的目标，不是现有实测成绩。**

测试分层包括单元/性质测试、组件、契约、端到端、图层视觉差异、性能、安全和离线安装/升级。核心算法与数据适配建议覆盖率 ≥80%，同时以高风险边界案例覆盖为主，禁止仅以覆盖率数字代替正确性。

计划提供统一一键入口，例如 `python tools/run_acceptance.py`：无需手工拼接参数，自带小型合成数据和默认配置，真实样例可用时加入回归；依赖缺失只输出清晰安装提示。该命令是后续实现的交付要求，**当前仓库尚未创建该测试入口**。

发布条件：需求追踪矩阵覆盖全部必交子功能；无 P0/P1 阻断缺陷；项目恢复、输出坐标对照、任务取消通过；模型/默认参数/依赖许可证和已知限制随包提供；新 Carto/游戏版本先做适配回归，不默认兼容。

## 3.【关键技术路线与难点预案】

### 3.1 架构与技术选型建议（须确认）

**推荐方案 A：本地优先的模块化单体，前端 GIS 工作台 + Python 算法进程 + 本地任务接口。** 原因是五模块共享几何、网络与需求，初期避免分布式服务带来的部署、传输、事务和排错成本。通过显式接口隔离，将来可替换算法或拆出计算服务，而不是一开始采用微服务。

**备选 B：QGIS 插件**，适合 GIS 专业用户优先、复用现有桌面编辑的路线；代价是工作流、打包及非 GIS 用户体验受宿主环境约束。采用哪条路线必须在 G0 确认，不在本次文档中擅自冻结。

| 层次 | 推荐候选 | 工程约束/PoC |
|---|---|---|
| 数据适配 | Python + GDAL/Rasterio、GeoPandas/Shapely、PyProj | 固定依赖兼容组合；P0 验证样例 TIFF、CRS、中文与大几何；GDAL 对 NoData 与仿射处理以驱动文档为依据 [R3] |
| 项目存储 | GeoPackage 存规范矢量/空间索引；GeoTIFF 或 COG 存栅格；独立工程元数据/情景记录 | GeoPackage 采用 OGC 规范 [R8]；不把大栅格反复塞入业务 JSON；写入事务与原子替换 |
| 算法底座 | NumPy/SciPy；图算法原型 NetworkX，热点改稀疏图；AequilibraE 分配适配；OR-Tools 候选设施/功能分配 | AequilibraE 有 FW/BPR 相关实现可作参考 [R6]；MIP 求解器可复用但每个模型需独立验证 [R7]；正式版本在 G0 冻结 |

| 测试与观测 | pytest 候选、前端单测与 E2E、结构化日志、作业指标 | 每个结果带输入/参数/模型版本和运行资源记录；日志不混入未经确认的游戏隐私数据 |

**安全要求**：导入数据视为不可信输入；限制文件/解压/几何规模，校验路径穿越，隔离解析失败，禁止执行导入文件附带脚本；默认不上传存档；本地服务不暴露公网；升级与导出前保留可恢复工程版本。

### 3.2 M1：用地规划

**完整能力**：陆地识别 → 城市用地/自然保护区区分 → 地形分区 → 自动功能分配 → 用户变更。

1. 基于规范水域/未知掩膜得到陆地；建立岸线、不确定带、禁止开发区与用户保护范围。
2. 从 DEM 派生坡度、坡向、局部起伏、相对高差和地形连通性；对地形适宜性进行栅格评分与区域合并，剔除碎小片，生成可开发分区候选。
3. 自然保护区采用“用户指定的硬约束 + 可解释的保护建议”双轨。缺少生态资源图层时降低结论等级，不把地形自动分区当成生态识别。
4. 按功能配额、建设强度、地形成本、可达性、环境冲突和连续性构造分配模型。先用规则/多准则排序保证可行，再以 MIP/局部搜索改善成本；权重归一化并保存。
5. 保持规划用地与游戏 Zoning 的映射表，混合用地、公共设施和保护用地可表达；不能强行把所有规划功能塞进单一游戏分区枚举。
6. 用户可改边界、功能、强度与优先级，可锁定要素；算法尊重锁定并解释冲突。硬约束解除须独立显式操作和审计。

**产物**：陆/水/未知、开发/保护及候选区、地形分区、功能用地、人口/就业推估、指标与冲突报告。

**难点预案**：配额/保护/地形约束无解时，先输出冲突集合与最小调整建议；不默认挤占保护区。需求资料缺失时报告低/中/高发展情景，不把默认容积率视为游戏事实。

### 3.3 M2：路网规划

#### A. TAZ 与逐区街区尺度

TAZ 按规划用地、河流/铁路等屏障、出行规模和网络可达性划分；行政区和游戏 Zoning 单元只是参考。TAZ 层保存独立参数：目标街区长/宽/面积、局部街网方向、支路间距、最小地块深度和路口密度限制。参数可以继承项目默认值，但修改后成为该区独立值。

街区生成采用地形约束的方向场/网格切分、候选路段连通与多边形化；边界与相邻 TAZ 的接口先约定，公共高等级道路共享，局部支路平滑过渡。更新局部参数不改变其它区域的人工锁定道路。

#### B. 交通规划四阶段法

四阶段是出行生成、出行分布、方式划分、交通分配；共享 LOS/广义费用反馈，不能把“画路网 + 最短路”称为完整四阶段法。[R10]

1. **生成**：分目的、分时段，基于居民/就业/设施或未来开发量构造产生量 $P_i$ 和吸引量 $A_j$；外部—内部、内部—外部、外部—外部过境及区内出行分别记录。缺失现状时使用明确的情景系数。
2. **分布**：双约束重力模型或等价熵模型，迭代平衡产生/吸引量；用旅行时间/广义费用作为阻抗；无路可达与跨水不可达需求不得硬塞给虚构道路。
3. **方式划分**：规则初值 → 多项 Logit 候选，考虑小汽车、公交、地铁/铁路、步行/骑行等可用方式；无服务方式不可被分配非零份额。先生成基础可用网络，再迭代公交方案。
4. **分配**：道路按车次与车型处理，人次向车次转换显式使用乘员率等参数；静态用户均衡采用 BPR/FW 类方法，公共交通按含接驳/候车/换乘的广义费用分配。[R6] 静态分配不用于直接估算队列溢出。
5. **反馈与停止**：公共交通/道路方案变动后更新阻抗和方式需求。外层迭代设置次数、时间与变化量阈值；保留最后可行方案和残差，不能只看几何稳定就宣称需求收敛。

候选需求模型：

$$
T_{ij}=a_i b_j P_i A_j f(c_{ij}),\qquad
\sum_j T_{ij}=P_i,\quad \sum_i T_{ij}=A_j.
$$

候选道路阻抗模型：

$$
t_a=t_a^0\left[1+\alpha_a\left(\frac{v_a}{C_a}\right)^{\beta_a}\right].
$$

**变量定义**：$T_{ij}$ 为分时段出行量，$P_i/A_j$ 为产生/吸引量，$a_i/b_j$ 为平衡系数，$c_{ij}$ 为广义阻抗，$f$ 为阻抗函数；$t_a^0/t_a$ 为自由流/拥堵旅行时间，$v_a/C_a$ 为同单位流量/容量，$\alpha_a/\beta_a$ 为待校准参数。所有参数均版本化；不直接套用现实默认值宣称符合游戏。

#### C. 外部连接与四级路网

- 现状模式：在项目边界/游戏外部网关、道路类别和连通图上识别连接候选，最终由适配验证或用户确认；普通悬挂端点不自动当作外部连接。
- 新城模式：将边界候选、外部道路方向和外部 OD 作为情景输入；缺少世界地图只优化研究范围内部分，标为假设网关。
- 候选路线采用成本栅格和方向/纵坡约束的 A*/最小成本走廊；需要曲率时引入方向状态与后续线形优化，而不是只运行普通像素最短路。
- 公路、主干路、次干路、支路分层生成并联合校核。类别由服务功能、可达性与需求建议，不只由现状 Category 或车道数决定。
- 桥/隧道作为独立高成本、受几何约束的候选边，不允许穿水体的普通地面道路蒙混过关。

**产物**：TAZ 与逐区参数、完整 OD 与方式需求、外部网关、四级道路、节点/转向、流量/饱和度/不可达与成本报告。

**难点预案**：网络设计为组合优化问题，首版采用分层候选生成 + 有界局部搜索，并输出多方案而非承诺全局最优；无完整需求观测时输出敏感区间。对无法收敛的模式反馈使用松弛和固定已确认供给的分阶段方案比较。

### 3.4 M3：内部道路规划

**完整能力**：地块出入口、内部微观组织、配建停车与公共停车同时实现。

1. **出入口**：沿符合接入等级要求的地块边界生成候选；筛选道路接入权限、距路口/匝道影响区的间距、坡度、车辆包络、内部可达和排队存储；用覆盖/成本模型选取主次入口。受控公路不允许地块直接任意开口。
2. **内部交通**：构造车行有向图、转向/冲突关系与步行图；实现单行组织、装卸/服务车辆路径、停车寻位和地块内外衔接，避免把所有需求接到一个质心连杆。
3. **停车**：按功能与时段建立停车需求曲线，分别输出配建需求、公共停车选址/容量、共享停车的峰值叠加与步行接驳；允许用户覆盖标准、容量与服务范围，不擅自套用某地区法规。
4. **微观评估**：先做静态可达、冲突与存储长度检查；局部 SUMO 研究区检验出入口排队、转向延误和回堵，信号数据缺失采用明确的假设方案。[R9]
5. **反馈**：向 M2/M5 回传接入点、转向需求、停车搜索交通及道路冲突，不把停车设施作为没有需求影响的图标。

**产物**：入口点及合法性、内部车行/步行线、转向关系、装卸/服务组织、配建与公共停车、时段供需、局部运行报告。

**难点预案**：缺少建筑面积/停车库存时采用显式容量与强度参数并显示不确定性；内部组织无解时返回地块尺度/入口权限调整建议，不凭空增开入口。微观运行结论标注为所用仿真器估算。

### 3.5 M4：公共交通规划

| 必交子功能 | 候选与算法方向 | 关键约束/评估 | 成果 |
|---|---|---|---|
| 海运外部连接走廊 | 连接水体、已知边界网关与港口候选的航行成本图；宽度/水深/转弯约束 | 必须连到已知或已确认外部可航网关；缺深度不能证明可航 | 海运外部走廊、多方案、能力状态 |
| 铁路外部连接走廊 | 地形最小成本走廊 + 方向状态搜索 + 曲率/纵坡优化 | 外部轨道网关、坡度、曲率、桥隧成本、结构层 | 外部铁路走廊、工程代价与限制 |
| 地铁线网 | OD 走廊提取、站点候选、覆盖/广义时间/建设成本的网络设计；规则基线 + 受限优化 | 地形/水域跨越、站距参数、换乘、线路负荷；施工地质未知 | 候选线网、站点、负荷与换乘 |
| 客运火车站及轨道 | p-median/最大覆盖候选选址 + 轨道接入与线形复核 | 网络步行/公交接驳、用地包络、进站坡度、曲率、扩展空间 | 站址、轨道走廊、枢纽关系 |
| 港口及航道 | 岸段候选、陆侧腹地与集疏运接入、船型约束下航道搜索 | 水深、宽度、回转空间、跨越物净空、外部可航连通 | 港址、航道、陆侧接入、可行性分项 |
| 公交客运站/枢纽 | 需求节点候选、网络覆盖/MIP 容量约束、换乘与停车协同 | 地块容量、公交进出、步行距离、折返/停靠、内部组织 | 客运站/枢纽选址、容量、接驳关系 |

设施选址和线网优化首先输出一个可解释规则基线，再提供改善方案，保存目标权重、约束和求解状态；不得仅最大化直线覆盖面积。

**海运特别门禁**：水体存在并不代表可航；评价应考虑设计船型、水深、航道宽度/转弯和通航空间，相关方法参照 USACE 导航工程指导思想，而不是把现实港航数值直接搬进游戏。[R11] 样例水深可以支持水深筛查，但船舶包络、桥下净空和外部航道连通仍需验证。若由 DEM 与 Depth 推导水面标高，先验证两者的游戏基准、地形是否表示水底及重采样语义，不直接相加作为确定事实。

**铁路/地铁特别门禁**：成本路径平滑后必须重新检查曲率、纵坡、净空和占地；缺地质资料的地下工程只标示风险，不给出确定施工预算。

**反馈**：更新公共交通供给、接驳/候车/换乘费用，重算 M2 方式划分与分配；输出总服务水平与拥挤/负荷。客货运及货运铁路/港口是否需要独立容量与物流模型，见待确认事项。

### 3.6 M5：公路入城规划

#### A. 连接点选址

在过境公路走廊与城市主干体系之间生成候选，综合服务覆盖、外部/过境 OD、主线与城市路网负荷、相邻接点影响、地形、用地与建设成本。采用候选组合搜索/MIP 与有界网络重分配，避免以“离市中心最近”作为唯一标准。保留过境与入城流的分离及合理绕行。

#### B. TIA 交通影响评价

TIA 按统一预测年份/时段/发展情景，至少比较：现状或基线、未来无建设、建设方案、建设加改善措施；无建设与建设方案保持相同外生发展假设，单列是否考虑诱导需求。研究范围依据受影响走廊、相邻路口和回堵传播设置，而不是固定圆形缓冲即结束。[R12]

流程：场景需求 → 接点与转向分配 → 主线/匝道/城市道路容量筛查 → 局部仿真 → 改善措施 → 再评估。输出流量/饱和度、旅行时间、延误、95 分位排队、储车长度/回堵风险和网络可达性；安全仅提供冲突风险代理，未校准时不预测事故率或法定 LOS 等级。

资料不足时输出基于假设的规划级 TIA、敏感区间与待补清单；没有观测不伪造校准报告。

#### C. 立交与匝道几何

1. **拓扑模板**：首版参数化支持与业务场景匹配的有限模板，例如菱形、喇叭形和定向衔接；按各方向交通关系生成，不仅摆放图形。
2. **平面线形**：直线/圆曲线/缓和段或明确的游戏曲线适配；检查设计速度、最小半径、曲率连续性、分合流位置与所需空间。
3. **纵断面**：利用 DEM 和道路/轨道结构层，生成受纵坡、竖曲线、净空及接顺约束的高程曲线；二维穿越线不能自动变成可行立交。
4. **衔接运行**：显式配置加减速段、织入/织出、车道及汇入关系；实际长度等采用已验证的游戏参数/用户标准，而非写死未经验证的现实值。
5. **占地与结构包络**：输出道路面、结构/边坡预留、冲突和简化土方指标；不当作结构设计。
6. **最终复核**：对平滑、模板拉伸和用户拖动后的最终几何重新检查；若不能满足约束则降为不可行候选并说明原因。

现实方法上，水平与竖向线形、匝道间距、视距和分合流应联合考虑，参考 FHWA/NCHRP 的工程方法；具体约束值由游戏适配与用户确认的设计标准决定。[R13][R14]

**产物**：连接点、转向需求、TIA 报告、立交有向拓扑、匝道平面线形/纵断面、占地与约束校核、游戏资产映射/未验证项。

**难点预案**：游戏曲线、道路预制资产和净空约束不清晰时，P0 做有限实际建造/对照试验，记录版本与参数。若无法满足几何或运营要求，尝试其它接点/模板；不通过放宽硬约束强行给出“可建造”方案。

### 3.8 结果解释与输出接口

所有模块输出同时包含几何/网络结果、指标、来源/假设、硬约束违反项、计算状态和用户锁定情况。状态至少区分：通过、警告、资料不足、无可行方案、未收敛、取消/失败。

**拟定交换成果**：GeoPackage 作为完整矢量成果；GeoTIFF/COG 为栅格派生层；GeoJSON 为轻量交换时使用明确的坐标变换；PDF/HTML 为方案报告；工程包包含参数、版本与依赖信息。游戏放样参考可输出项目/游戏坐标对应清单，但不等于自动导入。

报告至少提供规则基线、优化候选和用户编辑方案的同口径对比，并解释：为何在此布局、哪些约束控制结果、哪些假设最敏感、下一步如何调整。首版采用可解释规则与数学优化，数据不足时不引入难以校准的深度学习模型。
